**Phase 4 (done)**: RBAC (design doc §2.2) - two enforcement layers, both at the Postgres engine level, never relying on the LLM to make an authorization decision:
- **Table-level**: two real Postgres roles (`app_doctor`, `app_insurance_adjuster`, migration `7f3c9e2a1b4d`) with `GRANT`s matching the design doc's Data Access table (doctor: patients/encounters/conditions/observations/medications/procedures/allergies/careplans + `immunizations` since Timeline Tool already reads it; adjuster: claims/claims_transactions/payer_transitions/payers + encounters/procedures/patients, since the "Claim-vs-documentation consistency check" capability needs `procedures`). A query touching an ungranted table gets a real Postgres permission error.
- **Row-level**: RLS policies on every patient-scoped table, gated on session variable `app.patient_scope` (comma-separated patient ids), set via `SET LOCAL` inside the same transaction as the query (`app/rbac/policy.py`'s `scoped_connection`). Fails **closed**: unset scope -> zero rows, never everything.
- **JWT** (`app/rbac/security.py`, `python-jose`): encodes/decodes `role` + `patient_scope` claims. Makes no authorization decision itself - `policy.py` is what enforces.
- **Role-scoped tool routing**: `app.rbac.policy.TOOLS_FOR_ROLE` restricts what the Planner/Reviewer are even told exists (doctor gets all 5 tools; adjuster gets `sql`+`visualization` only, per the capability matrix's cost/comparative-analysis rows) - "different investigation goals, not just different column visibility" (design doc 2.2).
- Wired into `sql_tool.py` and `timeline_tool.py` (both accept optional `role`/`patient_scope` and run through `scoped_connection` when given) and the orchestrator (`run_investigation` validates `role` up front, threads it through every task and Reviewer call).
- **Two real bugs found and fixed while testing this, both more important than the RBAC plumbing itself**:
  1. The orchestrator's executive-summary generator was reporting a DB-permission-denied query the same way as a genuinely empty result - an insurance adjuster asking about medications got told "the patient is not taking any medications," which is false; the real situation was "you're not authorized to see this." Fixed in two places: `_summarize_artifacts` now explicitly flags a failed/denied query as `QUERY FAILED` (never silently `0 rows`), and the executive-summary prompt now explicitly forbids reporting a failure as a negative finding.
  2. The Planner's role-scoped tool list is a prompt instruction, not a guarantee - confirmed directly: it planned a `timeline` task for an `insurance_adjuster` investigation despite being told not to. The orchestrator only caught `NotImplementedError` before, so the resulting DB permission error crashed the whole investigation instead of failing that one task. Now catches any exception per-task, marks it `failed`, and continues - the DB-level boundary is what actually held, the fix just stops it from taking the whole investigation down with it. Also fixed a related `DetachedInstanceError`: `task.artifact` wasn't eagerly loaded before the session closed, only the parent collections were. A follow-up bug in this same fix hardcoded the failed task's `artifact_type` to `"sql_result"` regardless of which tool actually failed, so a failed `prediction` task's artifact was invisible to `sections["prediction"]`'s lookup - fixed with an explicit tool->artifact_type map (`ARTIFACT_TYPE_FOR_TOOL`), and `_summarize_artifacts` now flags ANY tool's failure clearly (`TASK FAILED`), not just `sql_result`'s (`QUERY FAILED`).
- **A third, more serious real incident found while testing this**: an LLM-generated query (asked to find "patients with similar characteristics to validate the prediction model's accuracy" - an over-ambitious task neither the Planner nor Reviewer should have proposed for a simple readmission question) ran a self-join comparing every patient against every other patient (matching gender + birthdate ±5 years + encounter date ±30 days) via a correlated subquery with no `LIMIT`. It ran for **18+ minutes** against real data volume before being found and manually killed via `pg_terminate_backend` - nothing bounded query duration before this. Fixed with a hard `statement_timeout` (`app/rbac/policy.STATEMENT_TIMEOUT_MS`, 15s), applied in both `scoped_connection` (covers every RBAC-scoped tool) and `sql_tool.execute_sql`'s non-RBAC path. Verified directly: a deliberate `pg_sleep(30)` query is cancelled at ~15.1s with a clean error, through both paths. This is a real production-safety gap any NL->SQL system has - an LLM will occasionally generate a query that's valid but computationally catastrophic (unindexed self-joins, missing `LIMIT`), and nothing except a hard DB-level timeout reliably stops it.

## Architecture (target — being built incrementally per the phase plan)

**Core philosophy:** only two components are "agents" — everything else is a deterministic-interface tool.
- **Planner** decides what evidence is required and emits a structured, inspectable **Investigation Plan** (task list) as its first action — it does not loop implicitly through tool calls.
- **Reviewer** checks whether gathered evidence is sufficient; can send the Planner back to insert more tasks, capped at 2 extra rounds, after which the Report generates anyway with `evidence_complete: false`.
- **Tools** (SQL, Timeline, Medication, Literature, Prediction, Visualization, Report) are plain deterministic code/LLM-calls with structured input/output — not agents. Timeline, Medication, and Prediction tools call no LLM at all.

**Four new persistent domain entities** sit on top of the untouched Synthea schema: `Investigation → Task[] → Artifact[]`, plus `Report`. Every tool call produces a typed **Artifact**; the Reviewer evaluates the Artifact set, not raw tool output; the Report is assembled entirely from Artifacts, keeping every claim traceable to its source.

**RBAC is enforced outside the LLM**: JWT → role resolution → row-level policy injected into the SQL Tool before any query executes. The LLM never makes an authorization decision. Two roles (`doctor`, `insurance_adjuster`) have deliberately *different investigation goals*, not just different column visibility — see design doc §2.2 before touching anything RBAC-related.

**Routing discipline matters**: the Planner should scope tools to the question (fast path: SQL-only or lookup-only for trivial questions) rather than always running the full pipeline. Over-invoking tools on simple questions is treated as a design defect, not a minor inefficiency — see design doc §3.6.

**Data source of truth is Synthea's schema, unmodified** — `Patient` is read directly from it, not duplicated into the application's own tables. LOINC and RxNorm are lookup tables (no ICD-10-CM — see Project status above); PubMed abstracts live in pgvector for the Literature Tool.

## Known dataset constraints (drive design decisions — don't design around data that isn't there)

- No free-text clinical notes anywhere in Synthea's output — every `TYPE == "text"` observation is a structured survey field, not a note.
- No claim denial/rejection state — `claims.STATUS*` is always `BILLED`/`CLOSED`. Claim questions must be framed as billing-lifecycle explanations, not denial reasoning.
- No drug-drug interaction data — RxNorm is a vocabulary, not an interactions DB. A hand-curated ~20-30 pattern interaction table is planned (Phase 3), not sourced externally.
- `medications.REASONCODE` links a med to the condition it treats on ~81% of rows (verified at the 2,338-patient dev scale) — this is the real causal-chain data backing the anchor "why did X change" scenarios; prefer it over LLM inference.
- `conditions.CODE` and `claims.DIAGNOSISn` are SNOMED-CT, not ICD-10-CM — verified against real loaded data (0 matches against a loaded ICD-10 table). Don't expect an ICD-10 lookup to resolve these; there isn't one in this schema (see above).
- `claims_transactions.PATIENTINSURANCEID` is **not** a `payers.Id` reference despite the name — it's `payer_transitions.MEMBERID` (a specific membership/plan instance). No FK on this column; see `app/db/models/billing.py` docstring.

See design doc §4.3.2 and §4.5 for the full findings list and rationale — don't rediscover these by re-exploring the CSVs.
